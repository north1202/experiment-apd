## A B S T R A C T

Deliberate academic misconduct by students often relies on the use of segments of externally authored text, generated either by commercial contract authoring services or by generative Artificial intelligence language models. While revision save identifier (rsid) numbers in Microsoft Word files are associated with edit and save actions of a document, MS Word does not adhere to the ECMA specifications for the Office Open XML. Existing literature shows that digital forensics using rsid requires access to multiple document versions or the user’s machine. In cases of academic misconduct allegations usually only the submitted files are available for digital forensic examination, coupled with assertions by the alleged perpetrators about the document generation and editing process This paper represents a detailed exploratory study that provides educators and digital forensic scientists with tools to examine a single document for the veracity of various commonly asserted scenarios of document generation and editing. It is based on a series of experiments that ascertained whether and how common edit and document generation actions such as copy, paste, insertion of blocks of texts from other documents, leave tell-tale traces in the rsid encoding that is embedded in all MS Word documents. While digital forensics can illuminate document generation processes, the actions that led to these may have innocuous explanations. In consequence, this paper also provides academic misconduct investigators with a set of prompts to guide the interview with alleged perpetrators to glean the information required for cross-correlation with observations based on the rsid data.

## 1. Introduction

Academic misconduct by students has increasingly become a problem, both in terms of outright plagiarism using sources readily available on the internet (Park, 2003; Awasthi, 2019) and in terms of commercially written material (‘contract cheating’), commonly disguised as ‘sample essays’ (Newton, 2018; Ahsan et al., 2022; Bretag et al., 2019a; Hill et al., 2021). The recent rise of publicly accessible generative Artificial intelligence (genAI) tools such as ChatGPT allow students to readily and effortlessly generate text for their assignments (Perkins et al., 2023; Weber-Wulff et al., 2023; Spennemann, 2023a; Cotton et al., 2023; Naidu and Sevnarayan, 2023). Conditions for abuse and academic misconduct have never been ‘better.’ This is not the venue to discuss the motivations and educational/societal conditions for such misconduct (Miles et al., 2022). As such misconduct threatens to undermine the integrity of the degrees and qualifications attained, all universities have processes in place to address academic misconduct through education and awareness training; through deterrence via detection and (graded) punitive action (Campbell and Waddington, 2020; Miron et al., 2021); and through modifications to assessment design (Bretag et al., 2019b; Harper et al., 2021; Chaudhry et al., 2023).

Current plagiarism detection software (e.g. TurnitIn) compare a submitted text with online sources as well as other documents submitted to the service. This method can detect verbatim plagiarism, but is less effective in detecting plagiarised text that has been ‘washed’ through online paraphrasing tools (e.g. https://www.wordtune.com, https://qui llbot.com). Texts written by genAI follow the same style of writing and expression, but will differ sufficiently in content to avoid software-based plagiarism detection (Spennemann, 2023b). Likewise, essay/assignment text that was written and supplied by other authors (commercial or not) escapes automated detection. Consequently, tools are needed that can be used by academics to i) identify submissions as suspicious and ii) interrogate these with regard to document authorship and genesis.

Building on crime prevention theory, Clare et al. noted that contract cheating and academic misconduct display patterns of non-randomness across offenders (i.e. submitters of work) and targets (i.e. institutions and specific teaching staff), which allowed them to develop suggested rule sets that can aid in the identification of potentially suspicious submissions (Clare et al., 2017). Among other indicators they include flags such as discrepant marks across assignments within and between subjects/courses taken by the student; variations in language and expression as well as changes in paragraph structure between other examples of student’s writing; and inconsistencies in formatting and type fonts within the same document (Spennemann et al., 2024).

Once flagged as suspicious, such work then needs to be subjected to a preliminary digital forensics investigation which examines the document for traces that are indicative of or may indicate the work as nongenuine. As this cannot be done from PDF versions, the original MS Word file will be required A preliminary digital forensics investigation involves an examination of the document properties such as document authorship, creation date and time, total editing time, and number of edits. If inconsistencies are found, or if the initial inconsistencies (e.g.

font etc) are deemed persuasive, a more detailed analysis is required.

This process needs to query the person who submitted the work with regard to the writing and editing process they followed with the document in question, which can then be cross-checked with a detailed digital forensics investigation (Fig. 1). The aim of any digital forensic investigation is to find what Jeong & Lee coined the 5WH1 (what, who, when, where, why and how) (Jeong and Lee, 2017). It is at that stage in the process that a detailed understanding of the nature and specific properties embedded in MS Word documents comes into play. MS Word files retain a considerable amount of information that can illuminate the document generation process. While it may not be able to answer the where and why of the modification, document forensics can illuminate the what and how, with some, albeit more limited, additional information on the who and when. This should be augmented by a structured interview with the alleged perpetartor of academic misconduct which elicits a detail set of information about the processes the document author followed in the generetaion of the document in question. Across-correlation of these assertions with the observations based on the rsid data will show congruence (probably innocuous) or dissonance (misconduct).

## 1.1. The file structure of MS word files

The Microsoft Office suite of applications has dominated the wordprocessing and document editing market on personal computers and tablets since the early 1990s (Mahlow and Piotrowski, 2022). The Office Open XML standard (ECMA, 2016; ISO/IEC, 2008) has been implemented in MS Word since 2007. Under this standard, all document components (text, styles, settings, meta data) are stored in a compressed archive, visible to the general user as a.docx file. Each new document is allocated a revision save identifier (rsid) at the point of document creation (rootrsid). This rootrsid persists when the file is copied, either through a ‘save as’ action in the editing software, or though copying the file at the operating system level (MacOs, Windows). Every document editing session that ends with a save action (or an e-mail send) is assigned an additional unique rsid number. These numbers, expressed as eight hexadecimal digits, are collectively stored in a summary table (‘rsidtbl’) in the file settings.XML (in the word subfolder) as a sequence in ascending numerical order (Spennemann and Singh, 2024). In the file document.XML (also in the word subfolder), each session rsid is then associated (in the form of enclosing tags, Table 1) with specific actions such as text insertions, deletions (if track changes was activated), and specific formatting such as the insertion of page and section breaks as well as subsections of tables.

The relevant standards (ECMA and ISO/IEC 29500–1:2016) stipulate that rsid should be randomly generated but with increasing numerical value, thereby documenting the progress of the editing (ECMA, 2016; ISO/IEC, 2008; ISO/IEC, 2016). A prior paper by the authors discussed the generation of rsid numbers and could show that while MS Word allocates unique and persistent rsid for each newly created document (rootrsid) as well as one persistent rsid for each edit session that is completed with a save action, it does not correctly implement these standards. The processes of generation and transmission of rsid numbers between different editing states within MS Word files have been discussed elsewhere and need not be repeated here in detail (Spennemann and Singh, 2024). Suffice to say that any newly allocated rsid may be smaller or larger than the document rsid (rootrsid) and the rsid of the preceding edit session (Spennemann and Singh, 2024).

## 1.1.1. Probabilities

MS Word allocates rsid numbers that can be up to eight digits long which equates to $1 0 ^ { 8 } – 1$ possible combinations (assuming that the overall number 0 is not a viable option). As a newly created Word document contains one document rsid (rootrsid) as well as one persistent rsid that is allocated to the first save action, $1 0 ^ { 1 5 } – 2 \times 1 0 ^ { 7 }$ possible rsid combinations exist. Assuming the file has seen one further editing phase ending in a save, which adds a further persistent rsid, the number of possible rsid combinations equates to $1 0 ^ { 2 \bar { 3 } } - 3 \times 1 0 ^ { 1 5 }$ (approx.). Thus the probability that two newly created Word documents share same the rsid combination by chance is close to one in a quadrillion, with the probability reducing to one in one hundred sextillion with one further editing phase ending in a save. In short, the probability of two documents having the same rsid combinations is infinitesimally small.

While theoretically possible, the probability that two independently generated files have the same rsid number allocated to an edit&save session is close to one in one hundred million $( 1 0 ^ { 8 } – 1 )$ —effectively 28 times smaller than the probability of winning first division in the lottery. This could theoretically occur, for example, where text is copied from one file to another with the rsid (in the pararsid or charrsid tags) retained in the copy process. The moment the chunk of copied text originates from a source text with more than edit &save actions, the number of rsid potentially carried over increases, while the probability of rsid combinations being the same by chance decreases exponentially. Thus, in theory, a document comparison between two independently submitted pieces of work should show whether and where copying occurred.

## 1.1.2. rsid numbers and version tracking in the literature

The usefulness and interpretation of rsid information for digital document forensics has been discussed mainly on a purely theoretical basis several authors (Didriksen, 2014; Ries, 2017; Garfinkel and Migletz, 2009; Fu et al., 2011, 2015; Fu and Sun, 2015; Joun et al., 2018, 2021; Langweg, 2012; Castiglione et al., 2017). Numerous approaches require access to the machine on which the file was generated or is stored (Jeong and Lee, 2017; Choi et al., 2021) while others require other document versions for comparative analysis (Spennemann and Spennemann, 2023). In the arena of academic plagiarism, however, it is usually only a single file that is available for analysis. Joun et al. looked at the existence of rsid in various word processing programs but did not examine the rsid allocation and persistence characteristics in any greater detail (Joun et al., 2021). Johnson & Davies, for example, postulated that rsid values night be useful in detecting or identifying contract cheating but did not elaborate of the mechanics of the analysis (Johnson and Davies, 2020) The authors have noted the potential usefulness of rsid numbers for the detection of academic plagiarism, in particular contract cheating (Johnson and Davies, 2020; Johnson et al., 2020, 2022). The authors commented that rsid numbers might be a tool to determine the chronological sequence of editing a given text. Theirs was a plausible assumption, given that the ECMA specifications for the Office Open XML standard stipulate that “every editing session shall be assigned a revision save ID that is larger than all earlier ones in the same file” (ECMA, 2016). The authors expanded on this by developing an (unpublished) tool that flagged whether a document text had been pasted as text chunk or whether successive editing had occurred in a document. While Johnson and Davies could show that rsid tags indeed signal the insertion of text between save events, and thus can be deployed to detect changes, but they could not demonstrate the validity of the chronology (Johnson and Davies, 2020; Johnson et al., 2020).

Fundamental to all papers is the assumption that Microsoft adhered to the implementation of the relevant standards (ECMA and ISO/IEC 29500–1:2016). As shown by the present authors, this is not the case (Spennemann and Singh, 2024). In consequence it is necessary to assess experimentally which of the editing processes leave tell-tale traces and what these traces look like. Some experimental work has been carried out (Spennemann and Singh, 2024; Spennemann and Spennemann, 2023). Experimental work by the authors confirmed that MS Word allocates a unique and persistent rsid (rootrsid) for each newly created document and that these, as well as the rsid allocated to edit&save actions (as stored in the rsidtbl listing), will persist even when files are copied at the operating systems level or when copied via a ‘save as’ action (Spennemann and Singh, 2024). Given that these rootrsid will be retained even if these copied files diverge in subsequent edit&save sessions, an given that the legacy rsid the rootrsid will also be retained, it is possible to develop document genealogies, showing common ancestor documents and branching from a common stem. This could be demonstrated experimentally by analysis over 400 MS Word templates for journal titles issued by an academic publishing house (Spennemann and Spennemann, 2023).

This paper extends the experimental work by emulating common author practices in the generation of documents such as copy, paste, moving sections of text, and insertion of blocks of texts from other documents.

## 2. Materials and methods

A number of experiments were designed to simulate and examine the effects of a range of common file management and document editing actions have on the allocation of rsid numbers in MS Word files.

## 2.1. Accessing rsid numbers

In the file settings.xml, the tag ‘rsidroot’ identifies the rsid allocated to the document itself. A summary table (‘rsidtbl’) stores all rsid numbers contained in a given document and lists them in increasing numerical order (Spennemann and Singh, 2024).

There are two fundamental ways of accessing and extracting the rsid information contained in MS Word files: by opening (unpacking) the. docx compressed archive file and examining the XML files which store the rsid numbers in hexadecimal format, or by examining the document as exported in rich text format (rtf) (Spennemann and Singh, 2024). This paper employs the second method (for process see Appendix A).

## 2.2. Revision experiments

## 2.2.1. Revision experiment 1

Revision Experiment 1 assesses whether pre-existing rsid influence the number of revisions as displayed in the property window of MS Word files (File > Properties > Statistics). To this effect a new file was created on the author’s (DHRS) MacBook (MS Word 16.54 build 21101001), which has in excess of 4000 rsid in the.dot/.dotm template file (Spennemann and Singh, 2024). Text was added to the newly created file followed by a save. In total ten iterations of text adding and saving were carried out. At each step, the ‘statistics’ panel of the ‘properties window was queried to ascertain the number of recorded revisions.

## 2.2.2. Revision experiment 2

Revision Experiment 2 assesses whether save actions without edits influence the recorded number of revisions as displayed in the property window of MS Word files. As base file served the document created for the Revision Experiment 1, which was saved under new name. Multiple save actions were performed, without changing any of the text. At each step, the ‘statistics’ panel of the ‘properties’ window was queried to ascertain the number of recorded revisions.

## 2.2.3. Revision experiment 3

Revision Experiment 3 examines whether times of inaction would influence the total document editing time as displayed in the property window of MS Word files. As base file served the document created for the Revision Experiment 1, which was saved under new name. That file was left open, with the ‘statistics’ panel of the ‘properties’ window queried after 80 min had passed (experiment 3A). A duplicate base file was opened and some text was added immediately, after which the file was left open the without a save action. The ‘statistics’ panel of the ‘properties’ window was queried after 20 min had passed.

## 2.2.4. Revision experiment 4

Revision Experiment 4 examines whether the total document editing time as displayed in the property window of MS Word files reflects actual editing time. As base file served a blank document created on the author’s (DHRS) MacBook (MS Word 16.54 build 21101001). Data were saved at 1-min intervals for five iterations, 2-min intervals for three iterations, 5-min intervals for two iterations followed by one 10-min interval. At each step, the ‘statistics’ panel of the ‘properties’ window was queried to ascertain the number of recorded revisions and the elapsed document editing time.

## 2.2.5. Revision experiment 5

Based on the unexplained increases in the number of revisions (as displayed in the property window of MS Word files) during revision experiment 4, a new file was created and subjected to series document processing events, each of which was followed by a period of time of inaction in the that file, while edit and save actions occurred in another document that was being worked on at the same time (in a different window). The events tested were ‘edit–wait period–save; ’ ‘edit–wait period—edit—save; ’ ‘edit—e-mail send—save; ’ and ‘edit—wait period–e-mail send—save.’ The ‘statistics’ panel of the ‘properties’ window was queried at each action (experiment 5A). To test whether the number of revisions would carry over to a file created via a ‘save as’ action, upon conclusion of experiment 5A the file was saved under a different name and additional edit&save actions performed (experiment 5B).

## 2.2.6. Revision experiment 6

The experiment was designed to assess whether the use of a legacy file would carry over the number of revisions and total document editing time data, or whether the total editing time would reflect the actual total time elapsed between the last document save and the current edit. A copy of a document that had been last saved on 28 January 2021 with two revisions and 3 min editing time was opened on 11 October 2022, then blanked and saved (6A). This was replicated with a copy of a document last saved on 11 October 2022, with 156 revisions and 196 min editing time (6B). At each step, the ‘statistics’ panel of the ‘properties’ window was queried to ascertain the number of recorded revisions and the elapsed document editing time.

## 2.3.1. rsid experiment 1

Rsid Experiment 1 examines differences between iterative generation of text in a single document and the insertion of iteratively generated text by copying or by read-in of the data. A set of three files was generated on a MacBook with MS Word 2011 (version 14.7.7) (experiment 1A) and a set of three files on a Windows PC using MS Word 2013 (version 15.0) (experiment 1B).

As base document served a file developed for and reported in a previous paper (blank MS Word file created on a MacBook, using MS Word 2011 [version 14.7.], saved, opened and text pasted in followed by a save & close action) (Spennemann and Singh, 2024). File 1 of each set comprised of the base document, which was opened and saved to rtf (to serve as control) file 2 comprised of the base document, which was opened, all content deleted (without a save action) and in the entire iteratively generated control text (see bellow for explanation) was pasted into the file via the clip board. This was followed by save action and save to rtf action. The process for file 3 was the same as that for file 2, with the exception that the iteratively generated control text was not pasted in but read in using the ‘insert file’ option.

The iteratively generated control text was text taken from a file with edit state 10 of experiment 3A as reported in a previous paper (Spennemann and Singh, 2024). The file was generated by opening a copy of base document, pasting in the derived text and saving it under a new file name. That file was reopened, pasting in further text, and saving it under a new file name. This continued iteratively until the ninth iteration. The final process involved adding lines between each of the pasted texts, resulting a file with 10 edit stages (Spennemann and Singh, 2024) with a complex rsid structure (Fig. 2).

## 2.3.4. rsid experiment 4

Rsid Experiment 4 examines the effects of swapping files between computers of different operating systems. Two variations were tested. The iterative, but sequential generation of text by adding a new line of text at each stage (experiment 3A) and the iterative generation of text, where at each stage, with track changes turned on, text was deleted, text was added, and the file then saved. ## 3. Results

The document creation time is frequently advanced as an argument that the document had been created over a prolonged period of time. Likewise, short document creation to document modification intervals are often seen as an indicator of untoward actions. The absolute time and date information as in contained MS Word files and retrievable via the document properties panel has little evidentiary value as it can be easily manipulated by disconnecting a machine from the network and resetting the clock to a desired time and date. Such virtual time travel is documented in the partial screen capture shown in Fig. 3a, where a file was seemingly created on 2 January 1980, four years before the first Apple Macintosh computer was launched on January 24, 1984 (Library, 1983) and five years before the first version of MS Word for the Mac appeared on the market (1985) (Knight, 2013). Fig. 3b shows a file which was created on 1 October 2022, but seemingly had been modified 42 years earlier.

## 3.1. Revision experiments 1 to 6

Revision Experiment 1 assessed whether pre-existing rsid influenced the number of revisions as displayed in the property window of MS Word files. The pre-existing rsid were not reflected in the number of revisions as displayed. These increased by one following each edit&save action.

Revision Experiment 2 assessed whether save actions without edits influenced the recorded number of revisions as displayed in the property window of MS Word files. Save actions without a prior editing event do not influence the number of revisions, nor the total document editing time, as displayed, and are also not reflected in the time modified entry.

Revision Experiment 3 examined whether times on inaction would influence the total document editing time as displayed in the property window of MS Word files. The total document editing time did not change after the file was saved which had been left open but otherwise left unchanged for 80 min. The duration the file was left open was also not reflected in the time modified entry (experiment 3A). In the file where text was added immediately after opening, but which was then left open for 20 min, the time stamp for the time modified entry changed, but the overall edit time did not.

Revision Experiment 4 examined whether the total document editing time as displayed in the property window of MS Word files reflected actual editing time. The results showed that the actual 1-min time intervals between save actions (following an edit action) are accurately reflected in the total editing time as recorded by MS Word. Once the intervals between save actions increased, the total editing time as recorded by MS Word diverged increasingly (Table 5). At the end of the experiment, the actual total editing time was 121 % greater than the time recorded by MS Word.

An ancillary observation was the fact that during the 5-min time intervals the revision numbers increased twice without actual save actions being carried out in the file itself. During that time other documents that were being worked on were being saved. Trials with a different document could not replicate these revision number increases. While the follow-up experimentation (revision experiment 5) could not replicate these, it confirmed inconsistent allocation of total editing time by MS word when compared to actual time elapsed.

Revision Experiment 5B tested whether the number of revisions would carry over to a file created via a ‘save as’ action. This was not the case. The revision numbering restarted at ‘1’.

Revision Experiment 6 was designed to assess whether the use of a legacy file would carry over the number of revisions and total document editing time data, or whether the total editing time as displayed would only relate to the file copy and reflect the actual total time elapsed between the copy event and the current last edit. In both cases the action of blanking out existing text with a subsequent save action resulted in an increase of the existing (legacy) number of revisions by one, with adjustment total document editing time by 1 min. The time of the last save was correctly displayed in time modified entry in the property window.

## 3.2. rsid experiment 1

Experiment 1 considered the insertion of a chunk of iteratively generated control text into blanked files. The control text contained eleven different rsid in a complex rsid structure (Fig. 2). The copy action via the clip board (experiment 1A), reduced the control text to single block of text, enclosed with a new rsid. The outcome was the same irrespective of whether a MacBook or a Widows machine was used. The copy action by reading in (‘insert file’) the control text (experiment 1B), maintained the complex rsid structure and tags, but replaced each of the eleven different rsid with the same new rsid. Again, the outcome was the same irrespective of whether a MacBook or a Windows machine was used.

## 3.3. rsid experiment 2

Since all file manipulation processes used file copies of the same base file, the rootrsid did not undergo a change in any of the files. The file operations on the MacBook resulted in the deletion of the temporary rsid in the sample file and the subsequent creation of a persistent rid as well as another temporary rsid, which is consistent with prior research (Spennemann and Singh, 2024). Neither the copy nor the read-in (insert) process added any of the rsid that had been contained in the generated control text files either in the rsid listing (rsidtbl) or the tags.

A comparison of the codes of the text as copied and as read-in to the test files with the code embedded in the control text itself, shows that all legacy edit codes that were contained in by the control text file were carried over into both the copied/read-in files (Fig. 4a–c). Importantly, the charrsid of the control text (charrsid9768227) was maintained and carried over, both in the pasting and the reading-in process (Fig. 4b and c). The text as read-in added additional codes, not marked with a rsid, which reflects different line breaks. Intriguingly, the line breaks differ between the original (Fig. 4a) and the two copy options (Fig. 4b and c). The insertion of the text, however, was characterised by a new insrsid that differed from the that in the legacy file from which the text chunk originated. By comparison, if the control text was not copied directly into the test file but first pasted into a text editor, with that text then pasted into the test file, all legacy edit codes were dropped. Also, in that instance the insrsid and the charrsid are the same. Running an update of the Endnote references, with no additional references inserted, does not change any of the rsid codes in the text.

## 3.5. rsid experiment 4

Experiment 4 examined the effects of swapping files between computers of different operating systems. The iterative, sequential generation of text (by adding a new line of text at each stage) (experiment 4A) allocated a unique, persistent rsid to each step, but these were allocated with both greater and smaller values (Table 6). The delete and insert actions with track changes turned on (experiment 4B) were also allocated unique, persistent rsid to each step, but, again, these were allocated with both greater and smaller values (Table 7). No systematic differences in rsid allocation could be observed between the Windows (W) and MacOs (M) iterations (Table 6, Table 7).

Once all track changes had been accepted, all tags containing tracking information disappeared, together with all rsid that indicated deletions and all time stamp data. All rsid associated with insertions, however, remained in place.

## 3.6. rsid experiment 5

Rsid Experiment 5 examined the effects of a complex series of file creation and editing processes on the allocation and persistence of rsid. The comparison of the typed text prior and after deletion events (Fig. 6a vs Fig. 6b) shows that an allocated insrsid persists as long as part of the originally inserted text (one or more characters or spaces) are retained. Where the entire text is deleted, the insrsid is deleted as well (viz. insrsid6302464 in Fig. 6a vs Fig. 6b). Although deleted in the body of the text, the rsid remains retained in the rsidtbl.

Modification of inserted text (bolding of first sentence, step E1) is reflected as a modification of the charrsid with retention of the prior insrsid: charrsid9715125 in the original typed text (Fig. 6a) is replaced with charrsid4341379 in the edited text (Fig. 6b). The same applies to edit step E6 were text was italicised (original charrsid11814380 vs charrsid7166929 in edited text, Fig. 6c and d).

## 3.7. rsid experiment 6

Rsid Experiment 6 examined the effects of blanking out existing text in a duplicate file generated a ‘save as’ action. All pre-existing rsid numbers were carried over. The temporary rsid allocated to the rtf save of the base file was dropped and a new rsid allocated to the inserted text was added. As the document was not closed and reopened between the last save and the save action to rtf, no temporary rsid was allocated.

## 3.8. rsid experiment 7

Rsid Experiment 7 examined whether the movement of existing text by dragging and dropping or by cutting and pasting would leave tell-tale traces. The internal movement of the text, irrespective of method, is a recorded as a text insert and thus is allocated the insrsid of the new editing session, whereas the charrsid remains that of the session that created the text. As an entire paragraph was moved, the new paragraph was also allocated a new pararsid tag with the same rsid number as the new editing session.

## 3.9. rsid experiment 8

Rsid Experiment 8 examined whether the legacy rsid contained in the insrsid and charrsid tags of a source file are added to the rsid listed in the rsidtbl of the analysis file. Given that the analysis file was created as a copy of the base document, it is unsurprising that the rsidroot is the same. The sample file dropped one temporary rsid from the Sample File and added one permanent and one temporary rsid, which is in keeping with findings of a previous study (Spennemann and Singh, 2024).

Significantly, none of the rsid carried in the copied text were inserted into the rsid table. The analysis of the rsid contained in the insrsid and charrsid tags showed that the analysis file contained 16 different insrsid numbers (associated with 1704 insertions), with the majority (1668) associated with a single insrsid number. This contrasts with a total of 2633 different insrsid numbers in the source file. While the reduction of insrsid numbers in the source file was considerable, that did not carry through the reduction of charrsid numbers (133 different numbers in the source file, 120 in the analysis file).

The repeat of the same experiment, using files with fewer legacy data, again showed that none of the rsid carried in the copied text were inserted into the rsid table. Importantly, the legacy rsid as contained in charrsid tags were retained but were not reflect in the rsidtbl of the analysis file.

## 3.10. rsid experiment 9

Rsid Experiment 9 assessed to what extent the initial generation of a document on GoogleDocs may have on the allocation of document rsid and rsid allocated during the editing stages. The generation of the test document had occurred in five stages with each following step only commencing after GoogleDocs’ automated save action had completed: typing in text of paragraph 1, text of paragraph 2, text of paragraph 3, bolding some words in paragraph 1, italicising some words in paragraph 2.

The first set of sub-experiments assessed how this edit sequence would be reflected in files downloaded from GoogleDocs. Examining the MS Word.docx file which had been created when the GoogleDocs was saved in that format, two significant observations were made: i) the MS Word file lacked a rsidtbl in the Settings.XML file; and ii) the five sequential edits remained visible at a fine-grained level with rsid tags, but with ‘00000000’ allocated as the rsid numbers of all edits. Opening a copy of the downloaded Word file and saving under a new name without any other changes generated a root rsid and two additional rsid in the Settings.XML file. While the Document.XML file containing the text showed a reduction of redundant rsid tags (dropping rsidRPr and rsidR but retaining rsidRDefault) and the replacement of most ‘00000000’ tags with the root rsid, the file retained evidence of the original edit sequence. Opening the downloaded file and adding a word followed by a save&close action also resulted in the allocation of a root rsid and two additional rsid to the Settings.XML file. Again, the Document.XML file containing the text showed a reduction of redundant rsid tags and the insertion of the root rsid at several instances of the original edit sequence, as well as the insertion of a new rsid for the added word. When the GoogleDocs file downloaded as a rtf file, a root rsid and one additional rsid were allocated, with the file showing a reduction of redundant rsid tags and the insertion of the root rsid at several instances, retaining evidence of the original edit sequence. ## 4. Discussion

When investigating allegations of academic misconduct, in particular contract cheating, it is desirable to be able to independently verify a student’s assertion of the document generation and editing processes. The limitations to tracking exact origins of text have been noted in the literature, but primarily from the angle of document comparison and integration (Filho, 2017; Filho et al., 2017), rather than digital forensics. While the extant literature noted the potential usefulness of rsid numbers for the detection of academic plagiarism, in particular contract cheating in general (Johnson and Davies, 2020; Johnson et al., 2020, 2022; Johnson et al., 2022), these papers erroneously assumed that MS Word would adhere to the ECMA specifications for the Office Open XML standard (Spennemann and Singh, 2024). Castiglione et al., claim that MS Word tracks all insertions and deletions, including the author attributes, allocating rsid numbers in the process (Castiglione et al., 2017). While this holds true for documents where the track changes features have been turned on, it does not apply to documents that are edited where the review function has not been activated.

Given that most student submissions are not submitted with the review function activated and, given that MS Word does not adhere to the ECMA specifications, the authors carried out a range of experiments to ascertain whether and how common edit and document generation actions manifest themselves in the encoding that underlies all MS Word documents. The underlying premise for much of document analysis is that document authors will develop their manuscript in an iterative fashion, comprised of a sequence of writing and editing (word & text deletion or insertion through movement), rather than writing a final, word-perfect text. The second premise is that the manuscript will have been created with repeated edit&save actions, especially if it was generated over the course of several days. The document properties (file ‘core.xml’ in the ‘docProps’ folder of the XML package) allows to assess the time elapsed between document generation and the last edit (also accessible with the properties window of the file in the MS Word).

For an examination of the evidence for the generation and editing of MS Word documents to be meaningful for the investigation of alleged academic misconduct, it is important that as much detail as possible has been gleaned by way of interview about the alleged perpetrator’s document generation and edit processes (see Appendix B), as this allows a forensic examination to turn these stated processes into scenarios that can be tested for veracity. The following investigative scenarios are based on real world examples that have been derived from personal experience of two of the authors (DHRS & CLS) as well as the experiences of colleagues, all of whom have had or currently have involvement with academic/student misconduct investigations at our institution.

Scenario 1: the properties panel of the document submitted for analysis shows that the document was recently created, has only a short editing time and a low number of revisions

Given the revision experiments reported earlier, a short editing time and a low number of revisions can be indicative of untoward action. Such property data can be generated when a file that contained numerous edits is saved under a new name or if text from another file is copied in toto into a blank file and saved. In the first instance, all preexisting (legacy) rsid are carried over from the old to the new document, which includes the rootrsid, all rsid listed in rsidtbl and all rsid associated with edit actions in the text itself. If the examination of the files that these legacy rsid are lacking, if there are discrepancies between the rsid listed in rsidtbl and the rsid contained in document tags, or if there is a large body of text without variation in insrsid and charrsid, then the evidence indicative of untoward action will follow patterns as described in scenario 3.

Short editing time alone can only be seen as indicative, however, as the time stamping of the total editing time, as reported as difference between the document creation and the document modification date can be inaccurate. While it had been noted elsewhere that MS Word only records time stamps in full minutes, omitting the seconds (Spennemann and Spennemann, 2023), compacted and non-linear lag in elapsed editing time has been observed in experiment 4. Of importance here is that time seems to be more compressed in instances of longer time gaps between save actions (Table 5).

Scenario 2: the properties panel of the document submitted for analysis shows that the document was been created some time ago, exhibits a considerable editing time and shows a high number of revisions

While prima facie the prolonged editing time and high number of revisions seems to suggest genuine document generation, it must be noted that, given the revision experiments reported earlier, it is possible to blank out a copy of an older document and thus carry over the document generation information of that file. If genuine, it can be expected that the total number of rsid associated with text insertion and edit events is largely equivalent to the total number of rsid listed in the rsidtbl, especially if the document was created on a windows machine. Moreover, all, or at least the overwhelming majority of insrsid and charrsid numbers in the text body should be reflected in the rsidtbl. See scenario 3.

If the document was reputedly generated on a Windows machine and the number of rsid considerably exceeds the total number of rsid associated with text insertion and edit events, then it is likely that an existing document was used with its original text blanked, thereby retaining the original document creation date and number of revisions made until that point and expands on the latter as new edits occur. This can be proven if as freshly created file (generated on the same machine) can also be obtained for comparison, in order to identify which legacy rsid are embedded in the.dot/.dotm template file.

Scenario 3: the document submitted for analysis was stated to have been developed over time, and no material is claimed to have been copied from other files

An iterative process of adding and deleting text will assign a different insrsid for each event that ends with a save action. These will be retained in the rsidtbl of the document. A genuine iteratively generated manuscript will exhibit numerous insrsid codes that represent that author’s writing and editing progress similar to the example shown in Fig. 2. If an inserted section of text contains additional snippets of edit and insertion codes that are associated with a charrsid not listed in the rsidtbl (e.g. Fig. 4b and c), then that chunk of text was copied from another MS Word file which contained that iteratively generated text.

If an inserted section of text lacks additional snippets of edit or insertion codes altogether, then that total section of text was either written in its entirety during that edit session or it was pasted in from another source. Such rsid-less, ‘washed’ text could have come from i) text lifted from a webpage or pdf document, ii) text copied from an email, iii) text copied from the output of a paraphrasing tool, or iv) text copied from the output of a generative Artificial intelligence program. It also possible that the rsid-less text chunk was generated in a text editor before being pasted in.

Pasting in from another source can be distinguished from extended typing by the presence of a charrsid that follows the insrsid (Fig. 5). Directly typed text, on the other hand, is only preceded by the insrsid of that editing session. The charrsid will be the same as the insrsid where the font (type, character size) of the pasted legacy text has been adjusted to conform with the format into which the text has been pasted (during the same edit& save session. The charrsid will differ if the font (type, character size) of the pasted legacy text has not been modified.

The copying and insertion of new text into files leaves tell-tale traces of the editing process. A chunk of text that had been generated over a series of edit&save sessions, and that had undergone a series of textual refinements, will contain a complex and often nested set of tags, with associated rsid numbers, that endure the copying process unless the text has been ‘washed’ through a text editor (Fig. 4d). Importantly, text copied from a different word file will be enclosed with two rsid tags, the insrsid tag that denotes the paste action itself and is associated with the then current edit session, and the charrsid tag that denotes the past edit actions of the text that had been pasted in. Both rsid numbers must be present in the rsidtbl (rsid Exp 8) if the paste action involved text that already existed in the current document and where the author merely rearranged the order of text. If the inserted text lacks a charrsid tag, then the text was moved during that edit session.

A mismatch between the insrsid and charrsid tags of the same paragraph should trigger a cross check with the rsid listed in the rsidtbl. If the rsid number of one or more charrsid tags is missing from the rsidtbl, then the text enclosed in those charrsid tags was copied or imported from a different word document. It should be noted that mere mismatch between insrsid and charrsid tags (which are both listed in the rsidtbl)does not indicate pasting of foreign text, as such a mismatch can also occur when some of the character formatting is changed in a different edit&save session.

If an entire word document, for example a contract-written essay, were to be copied into the clipboard and pasted into new Word document, then all insrsid tags of the inserted text would be same, while the charrsid tags might vary. If an output of a generative Artificial intelligence program were to be pasted en bloc into a new Word document, then the entire text would be devoid of rsid and be enclosed with a single set of insrsid and charrsid tags. In both instances, any additional framing, such as author attribution or (assignment) title, would appear different as they will have the same insrsid and charrsid tags of that, or a subsequent, editing session.

Finally, some comments with regard to the insertion of rsid-less text are warranted at this point. While the origin of the inserted section of text cannot be ascertained from the rsid codes alone, the nature and extent of the insertion can be determined. Despite this caveat, forensic examination of the text should consider whether the insertion of rsid-less text is limited to a single paragraph in a single edit&save session, whether multiple sections of rsid-less text have been inserted in the single edit&save session at different parts of the document; and whether multiple sections of rsid-less text have been inserted in multiple edit&save sessions. While innocuous explanations are possible, insertions of single paragraph segments of rsid-less text, that do not raise any similarity flags in programs such as TurnitIn are most likely the product a paraphrasing tool. This can be verified by comparing text in question with the original text as indicated by the reference (if given). While paraphrasing tools change the sentence structure, they will not alter the flow and sequence of the argument.

It is now possible from the analysis of the rsid whether a section of text has been written by a generative Artificial intelligence program. The insertion of multiple rsid-less sections of text in the same edit&save session, however, may well point to the use of the output of a generative Artificial intelligence program and its insertion at various points of the document. While various tools exist to detect Artificial intelligence generated text, they have varied levels of accuracy (Khalil and Er, 2023; Ventayen, 2023; Uzun, 2023; Habibzadeh, 2023) and usually rely on extended sections of text or whole documents. If the use of such AI detection tools is to be contemplated, it is recommended that the rsid-less sections of text are collated into a new ‘clean’ document and that this document is fed into the detection tool.

Scenario 4: the document contains chunks of text that appear plagiarised but show substituted words or part sentences and/or uses British instead of US American spelling

The copied section of text will be enclosed by an insrsid tag that presents the initial copying event. If the text was taken from another word document, then the insrsid and charrsid tags of the section will differ (with the charrsid reflecting the legacy rsid). If the document author carried out subsequent changes, such as word substitution or spellcheck (for example to correct US American with British spelling) in the same edit&save session, then this the substitutions and spelling correction will be enclosed with a pair of insrsid and charrsid tags carrying the same session rsid as the paste event. If the substitution or spellcheck was carried out at a later edit&save session, then the charrsid tags will be the same as that of the initial paste action, but the insrsid will reflect that of the later edit&save session.

Scenario 5: the document contains a chunk of text that appears plagiarised with a spurious reference at the end and a spurious reference breaking up the text

The copied text will be enclosed by an insrsid tag that presents the initial copying. If the references were inserted in the same edit&save session, then these references will be enclosed with a pair of insrsid and charrsid tags carrying the same session rsid as the paste event. If the references were inserted during a later edit&save session, then the charrsid tags will be the same as that of the initial paste action, but the insrsid will reflect that of the later edit&save session. If the insertion of the reference breaking of the plagiarised text occurred at later edit session than the insertion of the first reference, the then the charrsid tags will be the same as that of the initial paste action, but the insrsid will reflect that of the later edit&save session and thus differ from the rsid of the first reference insertion.

Scenario 6: the document shows observable inconsistencies in quality or style suggesting multiple authorship

The investigation of this requires a comparison of the editing characteristics of the paragraphs that differ in quality or style. If they were written by the same author, the text creation and editing pattern should be the same or very similar. The pasting of pre-existing text from a different document can be detected looking for differences between the insrsid and the charrsid that follows (see scenario 5).

Scenario 7: the document supplied is an old, early draft, which is provided as evidence of prior own work

For this analysis two versions will be in hand. Setting aside issues of creation and modification dates that can be manipulated (see above), all rsid listed in the rsidtbl of the draft version must also be present in the submitted version. As the final version would comprise at least one more edit&save action, the number of rsid in the final document must be greater than that of the draft document. These additional rsid must be associated with edits and additional text that is not included in the draft. If, instead the ‘draft’ version was created by reverse-editing the final copy, the number of rsid in the rsidtbl of the draft version is likely to be as high or higher than the submitted copy and will differ by at least one rsid from the final version.

## 5. Conclusions

This study has shown that revision save identifiers (rsid) are a powerful tool for document analysis as they will leave traces in MS Word files which provide evidence of the creation and editing processes used to shape a specific document. These traces include the ability to detect differences between iterative text generation in a single document and inserting iteratively generated text by copying or reading-in data; between typed and pasted text in the same edit session, and between existing text that was moved dragging and dropping as opposed to cutting and pasting. In addition, traces of legacy edit events and legacy rsid (in charrsid tags but not rsidtbl) are retained when inserting prior generated text. In itself, however, such evidence only illuminates the document generation process, but does not provide evidence of academic misconduct.

To be meaningful, it is necessary to glean, by way of interview with the alleged perpetrator, as much detail as possible about the asserted generation and edit processes that led to the document to be examined. Appendix B provides a suggested set of interview questions as well as the rationale why this information is useful. A forensic examination of the rsid patterns in the disputed document allows to test the veracity of the author’s assertions, thereby confirming or refuting allegations of academic misconduct. It should be noted, however, that this validation of allegations of misconduct is merely tool and as such entirely separate from any educative or punitive action that may flow from these findings.

## Appendix A. How to access rsid numbers

## Method A: rsid in hexadecimal format

Every file in Word.docx format is in fact a compressed archive of multiple files, which can be easily accessed by replacing the ‘.DOCX’ extension of the file with ‘.ZIP’ and then extracting that archive using standard decompression/de-archiving software. The resulting file folder contains three subfolders. The required files are located in the ‘word’ subfolder. All rsid numbers are rendered as hexadecimal characters (e.g. rsid004C4A41) and stored in the file settings.xml. The body of the text document, is stored in the file document.xml where all editing and formatting tags carry rsid numbers (as hexadecimal characters) that correspond with some of the rsid listed in the settings.xml file. As MS Word cannot open these files, they need to be read using a plain text editor such as TextEdit or Notepad. All rsid numbers contained in a given document are stored in a summary table (‘rsidtbl’) which lists them in increasing numerical order. In addition, the tag ‘rsidroot’ shows the rsid allocated to the document itself.

## Method B: rsid in whole number format

The benefit of this approach is that all rsid numbers are rendered as standard numerical strings (e.g. rsid4999745) which are more comprehensible for the lay person than numbers in hexadecimal format (i.e. rsid004C4A41). The process requires the user to save the file in rich text format (.rtf), to open that file in MS Excel or a Text Editor that does not attempt to interpret the rtf file, delete the first line of code and then to save the file as text (.txt). Thereafter the coding of the file can be read using MS Word or a plain text editor such as TextEdit or Notepad. All rsid numbers contained in a given document are stored in a summary table (‘rsidtbl’) which lists them in increasing numerical order. It should be noted that exporting to rtf adds a temporary rsid (reflecting this save action, which not contained in the xml file. This does not affect the interpretation of any of the rsid in the text edit sequences.
